# Credits are metered in the Turn control plane, and the refund guard is chat's

**Status:** accepted

**Related:** [ADR 0006 — entitlements injection seam](../../../../../docs/adr/0006-entitlements-injection-seam.md) (the provider seam this rides on), [ADR 0003](0003-conversation-ownership-as-middleware.md) (ownership runs first), [ADR 0004](0004-generation-worker-and-queue.md) (the worker that refunds)

## Context

Chat is one of two slices that spend money per request, and the only one that
spends it on work that outlives the request. A Turn is enqueued, generated by a
worker, and may end in a way the user did not choose — an LLM error, or a worker
that dies mid-generation and leaves nothing behind. So chat cannot treat
metering as a gate at the edge; it needs a ledger that survives the request that
opened it.

The provider seam itself is settled elsewhere: credits are read, consumed and
refunded through the injected `EntitlementsProvider`, which is why `@acme/chat`
has no dependency on `@acme/subscriptions`. What that ADR does not decide is
_where in a Turn_ the spend happens, _which endings_ give the credit back, and
what consistency chat can actually offer across a seam it deliberately cannot
see behind. Those are this ADR's.

## Decision

**The consume is inline in `chat.send`, positioned inside `beginTurn`.** There
is no metering middleware — the shared `rateLimit` middleware was applied to
zero procedures and has since been deleted. `send` resolves entitlements once
itself, then passes the gate-and-consume to `beginTurn` as a closure, which runs
it after the In-flight lock is won and the user Message is persisted, and before
the job is enqueued.

Every part of that ordering is load-bearing:

- **After ownership** (the builder ran first), so a `FORBIDDEN` / `NOT_FOUND`
  request spends nothing.
- **After the lock**, so the losing tab of a two-tab race returns
  `alreadyInflight` having spent nothing — the race cannot double-charge.
- **Before the enqueue**, so exhausted credits produce `TOO_MANY_REQUESTS` with
  no job in the queue. A rejected send leaves no work behind and no held lock:
  `beginTurn` unwinds on any failure of the closure.

**Refunds are owed on the endings the user did not choose, and only those.**

| Terminal    | Refund | Why                                                   |
| ----------- | ------ | ----------------------------------------------------- |
| `done`      | no     | The user got the answer.                              |
| `cancelled` | no     | A Stop is a choice, and it consumed a partial.        |
| `error`     | yes    | The worker refunds; nothing was delivered.            |
| orphaned    | yes    | `chat.reconcileTurn` refunds a crashed worker's Turn. |

Both refund paths cross the **same** provider seam as the consume — the worker
through the provider its app's composition root built, `reconcileTurn` through
`ctx.entitlements.refund`. A billing swap therefore changes one adapter rather
than two, and a slim app refunds nothing without importing a billing package.

**The idempotency guard is chat's, not the provider's.** All refunds pass
`refundTurnCredits`, whose `chat:refunded:{turnId}` `SET NX` admits exactly one
refund per Turn, so the worker's error path and a concurrent `reconcileTurn` can
race freely. The guard lives in `chat-turn-lifecycle.ts` with the rest of the
Turn control plane, because "has this Turn already been made whole" is a fact
about a Turn — a concept the provider has never heard of.

## Considered and rejected

- **Meter with a tRPC middleware.** The obvious shape, and the one the seam ADR
  originally described. It cannot express the ordering above: a middleware runs
  before the procedure body, so it charges before the lock is contested and a
  duplicate tab pays for a Turn it never gets. Rejected — the charge belongs
  where the Turn is actually begun.
- **Refund on `cancelled` too.** Kinder, and wrong: a Stop persists the
  non-empty partial as a Message, so the user keeps output they asked to keep.
  Refunding it makes Stop a free retry. Rejected.
- **Put the idempotency guard behind the provider.** It would fuse the guard and
  the credit-back into one write and close the residual below. It also means
  handing the provider chat's `turnId` vocabulary and requiring every
  implementation to honour it — including `unlimitedEntitlements`, which has
  nothing to be idempotent about. Rejected here; see below.
- **Refund first, then set the guard.** Rejected — see the bias below.

## Consequences

- `@acme/chat` depends on no billing implementation. That is the canary: if the
  seam ever leaks, this package acquires `@acme/subscriptions` and the leak is
  visible in a `package.json`.
- `send` is the only chat procedure that resolves entitlements, and it does so
  once per call. Read-only chat queries pay nothing for billing.
- Tests assert the contract chat owns — the `refunded` result, the guard, and
  that the error path crosses the injected provider — against a structural mock.
  Whether a balance actually moved is `@acme/subscriptions`' test to write.

### The residual, named and accepted

The guard write and the credit-back are **two writes on two keys, and chat
cannot fuse them.** The credit-back lands on storage only the provider may name,
which is exactly the property that keeps this package free of billing. So a
crash between the two leaves a Turn marked refunded with the credit not
returned.

The ordering is a deliberate bias, not an oversight:

- **Guard first** loses at most one credit, once, on a crash.
- **Refund first** mints a credit on every crash, because the replayed
  `reconcileTurn` would refund again.

The guard is also **permanent** — nothing clears `chat:refunded:{turnId}` — so a
replayed or malicious `reconcileTurn` can never over-credit, which is the
failure mode worth spending a credit to avoid.

Closing the gap requires the credit-back to carry chat's idempotency key
_across_ the provider seam, which is an amendment to the entitlements seam ADR
and a change to every provider implementation. Deliberately not taken (#198).
